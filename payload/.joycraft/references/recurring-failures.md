# Recurring failure guidance

Use this reference only when a coordinator sees a possible reusable lesson in
existing independent `FAIL`, `UNVERIFIED`, or later verified-repair reports.
Keep a compact, source-linked shortlist in the active task material, not a new
state store. An empty shortlist is useful when the reports do not support one.

## Select and inspect

Treat distinct tasks or incidents as separate evidence; repeated attempts at one
failure are not independent episodes. A single verified repair can establish a
project fact about that repaired behavior, without waiting for two episodes.
For each candidate, inspect the current owning sources before repeating any
historical claim: a past report may be stale. Keep its report/receipt path, the
scoped trigger or counterexample, and the actual counterpart paths or journey
that distinguish the affected behavior. First check whether existing guidance
and relevant sources were declared, delivered to the worker, and actually read
where the transcript establishes that. Repair missing delivery before adding
more instructions; an input hash proves delivery, not comprehension.
Do not turn a local observation into a
global rule, rewrite unrelated guidance, or add an approval, blocker, schema,
runtime, provider call, or automatic rewrite.

## Deliver and assess

Frame an unverified generalization as a proposed lesson. Send a reviewed
proposal to the next worker through the existing [dispatch guidance](dispatch.md):
include its report links, current source paths, trigger/counterexample, actual
counterpart path or journey, and the concrete check to perform as exact worker
inputs. After one verified repair, link the outcome as a project fact about that
fix. Context and proposed lessons do not create product decisions, permission,
binding constraints, or an expected review verdict. Claim a broader method benefit only after later independent reuse confirms
it; until then, keep that benefit pending rather than presenting it as evidence.
