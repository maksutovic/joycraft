# Joycraft Retro

Use when the user requests a retrospective. Review their selected session, or
the current session when none is specified. A successful final result can conceal
expensive searches, retries, missing inputs and workarounds. This is an optional
diagnostic of how the work happened, separate from code acceptance and session
closure.

Read the session's actual record and relevant current project sources. Keep the
user's instructions, tool activity and agent claims distinct. Follow links to
necessary worker records or receipts within the requested scope; disclose missing
continuations, unsupported records and uncertain chronology. A final summary,
input hash or passing test alone does not establish what the agent understood.
For native logs, use [evidence preparation](../../../.joycraft/references/retro.md#prepare-native-session-evidence)
when it saves repeated parsing. Use explicit sources or the host's current
session, rather than searching unrelated projects or global private settings.

Find observed friction, including navigation, missing source delivery, broken or
unwired checks, overlooked reviewer judgment, expensive tools, instruction sprawl
and unavailable information. Inspect existing tooling before proposing another
check. Connect each candidate to an exact session moment and the current owning
source; distinguish an agent mistake from a stale decision, missing delivery,
missing capability or an incorrect tool. Frustration is a lead, not proof of the
cause. A quiet costly issue can outrank a loud cheap one.

Prefer the smallest supported remedy: repair a tool or check, improve a scoped
context pointer, or clarify reviewer guidance. Mechanically detectable failures
belong in deterministic checks when those checks earn their maintenance cost.
Keep implementation-critical guidance available to implementers. Retain product
choices in their existing brief authority. Removing ineffective instructions is
a candidate for a behavioral comparison, not a conclusion from one smooth run.

Present a short prioritized report: **what happened → evidence → proposed remedy
and its home → how to test it**. Separate measured cost from estimates and report
coverage limits. Keep additional supported findings available through disclosure
or linked detail. An empty candidate list is a valid result. Use a small visual
or before/after when it makes a finding easier to judge.

Recommendations stay proposals. A retrospective request does not authorize
editing skills, global instructions, permissions or project behavior. Honor any
specific remediation already authorized by the user without asking again; keep
other candidates for selection. A selected repair needs the failure case and a
legitimate counterexample checked before becoming guidance. Preserve acceptance,
archive timing and current human authority; a lesson cannot add a permission
gate or certify a PASS. Use [recurring failure guidance](../../../.joycraft/references/recurring-failures.md)
when delivering a chosen lesson to later workers. Claim general benefit only
after later independent reuse supports it.
