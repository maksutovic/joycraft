Read-telemetry is feasible today; the skill changes are reorders, not rebuilds

Codebase research answering two questions: can Joycraft count reads and writes of context docs from existing harness transcripts, and what must change in the skills to follow Mario Zechner & Armin Ronacher's curated-harness guidance. Read the verdicts, then approve the hand-off to design.

Question A

Read-telemetry feasibility, per harness

Every harness on this machine already writes per-session JSONL transcripts to a per-project directory. A write-never-read audit is a scan over those files — no telemetry infrastructure, no network. The fidelity differs by harness.

Claude Code — trivial

~/.claude/projects/<slug>/*.jsonl. Read, Write and Edit calls carry a structured input.file_path field inside tool_use blocks. A jq filter yields per-doc read/write counts directly. 6 sessions, 12MB here.

Pi — feasible

~/.pi/agent/sessions/--<cwd>--/*.jsonl, typed event lines with cwd in the session header, plus run-history.jsonl. 31 joycraft sessions on disk.

Codex — degraded

~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl (1,534 files, 6.2GB). File operations appear as exec_command shell strings — detection means parsing command text, not reading a field. Ship best-effort, second.

Question A

Boundary and integration facts

  • Precedent for reading outside the project exists: src/frontmatter.ts:115 already derives ~/.claude/projects/<slug>/memory/ for owner resolution. The AGENTS.md boundary forbids absolute paths only in shipped template/skill text.
  • optimize v2 already defines the landing zone: five evidence labels (VERIFIED requires a mechanical check this run) and six dispositions — a transcript scan slots in as a new VERIFIED evidence source, no vocabulary change.
  • The transcript directory also holds the auto-memory dir; joycraft-owner.txt lives there and must survive any cleanup step (git-config fallback covers deletion).
Question B

Open

Questions for you

Q1

What staleness threshold flags an ungraduated discovery?

Recommend: 60 days from the created: field, checked by optimize (advisory, never auto-delete).

Discoveries already carry created dates, so a day threshold is deterministic and testable; a releases-based trigger would couple the check to publish cadence, which varies. This is a proposal awaiting your word, not a settled fact.

Q2

Does the transcript scan run automatically inside optimize, or as an opt-in audit?

Recommend: automatic in optimize for solo installs, with a one-line skip when the session dir is absent; document that it reads local transcripts.

The scan reads only the user's own machine-local transcripts — the same directory optimize already touches for settings audits — but on team projects a teammate's install may see this as surprising, so the docs must say it plainly. Opt-in would gut the evidence value since nobody runs optional audits.

How to answer

Say "approved" (with answers to Q1/Q2, or accept the recommendations) and the hand-off to /joycraft-design proceeds with these findings locked. Ask for changes by naming the section and what is wrong, and the research doc is corrected before design. If the framing itself is off — wrong questions, wrong split of the work — reject it outright and say what the right framing is; nothing here is committed to specs yet. Answers land in the brief and the decision log.
