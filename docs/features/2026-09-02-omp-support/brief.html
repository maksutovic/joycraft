omp becomes the fifth harness: skills now, runtime later

Shape

What omp needs and what it already reads

Every row here comes from the omp v18.1.5 documentation bundled in the local install (omp read omp://...) or from the Joycraft source. Rows marked proposal are agent choices stamped as D8 and D9.

omp ignores .pi/

omp reads none of .pi/skills, .pi/extensions, or .pi/agents. Its native project root is .omp/. Nothing Joycraft installs for Pi reaches omp. Verified in the docs.

omp already reads three Joycraft trees

.claude/skills (priority 80), .agents/skills (70), and .github/skills (30) are discovered today. A native .omp/skills entry wins name collisions at priority 100, so the omp-flavored copy shadows the others.

Root context files load as-is

omp loads the root AGENTS.md and CLAUDE.md and expands @ imports. D2 writes no native copy. Sticky .omp/RULES.md stays out of scope.

Invocation mirrors Pi (proposal, D8)

Users invoke /skill:<name>. The model reads skill://<name>. /new starts a fresh session. The transform row copies Pi's values with .omp/skills as the directory.

Boundaries

What every spec must respect

Must
  • Add omp to the harness enum and every per-harness gate in init, upgrade, and gitignore
  • Generate src/omp-skills/ from src/skills/, never edit it by hand
  • Keep every omp skill flat at .omp/skills/<name>/SKILL.md with a non-empty description, because omp discovery is non-recursive and rejects skills without one
  • Include omp in the multiTool expression so an omp-only install writes the pointer CLAUDE.md
  • Commit regenerated bundles and the installed .omp/skills tree in the same commit as any skill edit
  • Touch CHANGELOG.md and name the D5 side effect: legacy-state projects gain .omp/skills on upgrade
Must not
  • Write .omp/AGENTS.md, RULES.md, config.yml, extensions/, agents/, or scripts/
  • Add a runtime dependency
  • Reference an absolute path in a generated skill
  • Port the Pi headless runtime in this feature (backlog file written)
  • Add omp deny patterns to harden or lockdown (backlog file written)
  • Add a live omp -p smoke test to CI
Hazards

Traps the specs inherit

Harness blocks are allow-lists

The 22 skills hold 68 harness: blocks. omp inherits none until spec 3 names it in each. Adding omp to the enum without the audit ships skills with no output-style pointer and no gate contract. Verified.

Pi blocks lie to omp

Ten blocks are Pi-only and several name joycraft-implement-loop or a .pi/ path. None of that exists for omp. D9 gives omp the Codex and Copilot no-runtime text for those. Verified.

.omp/ non-empty activates project settings

Installing skills alone makes .omp/ non-empty, which turns on omp's project settings layer. No settings file is written, so the layer is empty. Verified.

Collision warning (unverified)

When Claude and omp are both selected, omp sees each skill twice. Native wins. omp can print a startup collision warning. This is cosmetic and was not tested live.

  • Upgrade on a project whose state lists omp rewrites a hand-edited .omp/skills file and leaves user files alone
  • joycraft telemetry counts a session written under ~/.omp/agent/sessions/
