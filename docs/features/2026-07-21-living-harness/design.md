## 1. Current State

**The pilot gate chain already exists and is the substrate for Half A.**
`joycraft-new-feature` and `joycraft-design` invoke `/joycraft-decide`, which stamps a
`decisions:` block into brief frontmatter; `joycraft-decompose` Step 1.5 reads that block
as its **single source**, fails closed on parse errors, and blocks on any `status: open`
(`.claude/skills/joycraft-decompose/SKILL.md:23-35`). `joycraft-decide` is repo-local only
(no `src/` counterpart); decompose/design/new-feature diverge from `src/` behind
`<!-- PILOT -->` markers citing decision-dossier brief decision #7.

**Knowledge layer** (`docs/context/`): four populated docs. `decision-log.md` (42 lines) is
the closest thing to a ledger — `| Date | Decision | Why | Alternatives Rejected | Revisit When |`
rows, **append-only newest-last** per `joycraft-add-fact` SKILL.md:132. No shipped ledger
exists anywhere. Discoveries are flat files in `docs/discoveries/` (~21) with the 4-field
personal frontmatter schema (newer ones; pre-2026-05-21 files have none). No overlap check
at write time — add-fact routes but never greps for near-duplicates.

**Feature status is fragmented across three signals that disagree:** brief frontmatter
`status:` (present in only 10 of ~38 briefs), the `-draft` folder-name suffix (11 folders),
and per-feature `.joycraft-spec-queue.json` (`todo/in-review/done` per spec). 47 feature
folders exist; exactly 1 brief says `done`. RF-4's "29/43 never built" is confirmed live.

**Enforcement surface:** `.claude/settings.json` carries `permissions.allow/deny`, a
SessionStart version-check hook, and a PreToolUse Bash gate — `block-dangerous.sh` greps
`deny-patterns.txt` and `exit 2`s on match. All generated by `src/safeguard.ts`
(`generateHookScript`, `getDefaultDenyPatterns`, `installSafeguardHooks`) and installed by
`init.ts:411-414`. `joycraft-lockdown` is advisory-only (emits suggested NEVER rules +
permission strings, never auto-applies). `joycraft-optimize` is a read-only length/plugin
audit (≤200-line thresholds, description-budget check) with no semantic dispositions.
`joycraft-tune` scores 7 dimensions; boundaries are scored as declared, never verified.

**Config/state:** `src/version.ts:20` sets `STATE_PATH = docs/.joycraft/state.json` (this
repo still has legacy `.claude/.joycraft/state.json`, v0.6.10, not yet migrated). state.json
is **gitignored** and holds only `{version, files: {path→hash}, gitignoreProfile?, harnesses?}`.
No model/tier field exists anywhere in `src/`.

**Research corpus:** the brief's lossiness warning is confirmed. Premise-dependency chain
linking and confidence-gap deepening exist **only** in `research/ce-vs-joycraft-claude.md`
(:236-237, :168-171), not in convergence.md. Confidence anchors {0,25,50,75,100} with CE
thresholds (≥80 code / ≥75 / ≥50 doc) at claude pass :125. Six dispositions + evidence
labels (`VERIFIED|USER_REPORTED|INFERRED|INACCESSIBLE|NOT_APPLICABLE`) are Nate-doc vocab
(:59-63), not RF-panel vocab. Model-tiering brief proposes tier maps + "recommend main-loop,
enforce on subagent spawns" but deliberately left the config encoding open (its D1).

## 2. Desired End State

**Half A — decide precisely:**
- **S1:** decompose writes each spec constraint/AC with a provenance cite (`[src: D3]`,
  `[src: design §2]`, `[src: brief "Constraints"]`); anything uncited is auto-labeled
  `[src: INVENTED]` and surfaced in the decomposition table before spec generation.
  `joycraft-verify`'s oracle re-pointed to the human-approved brief + boundaries.
- **S2:** a new `docs/context/anchors.md` defines {0,25,50,75,100} once (S10's Phase-0
  spine); design/new-feature attach anchors to load-bearing claims; decide blocks
  propagation of load-bearing claims at ≤50 — they deepen or become dossier questions.
- **S3:** research, design, and decompose each open with a bounded grep-first retrieval
  pass over `docs/context/` + `docs/discoveries/` + the ledger, and cite what they reused.
- **S4:** add-fact and session-end grep for an existing home before writing; overlap →
  update in place, never a near-duplicate file.
- **S5:** a shipped ledger (shape = D2) + a refresh lifecycle
  (Keep/Update/Consolidate/Replace/Delete, deletion gated by inbound-link grep); session-end
  on a merged `done` feature writes the ledger row, confirms decision rows landed, then
  deletes the feature folder (trigger = D1).

**Half B — keep the harness true:**
- **S6:** a harden pass (home = D3) converts eligible ALWAYS/NEVER prose into
  `permissions.deny` strings and `deny-patterns.txt` regexes via the existing safeguard
  machinery; at least one Joycraft boundary converted as proof.
- **S7:** every boundary rule carries origin + date provenance; model upgrades put rules on
  probation; tune labels boundaries `declared` vs `verified`.
- **S8:** optimize v2 emits a six-disposition table (KEEP/ONE_HOME/LOAD_LATER/MAKE_A_CHECK/
  PROBATION/RETIRE) per material control with cross-file duplication detection; the Reaper
  archives undead feature folders to `docs/archive/`.
- **S9:** session-end gains a "promote to harness" step that **proposes** (never applies)
  repeated discoveries as boundary rule, context fact, or project skill.
- **S10:** anchors.md + a PROTOCOL-vs-JUDGMENT authoring rule + a minimal fresh-subagent
  eval (N≥3) applied to skills this sprint changes.

All changes are repo-local `.claude/skills/` + `docs/` with PILOT markers; `src/` untouched
until pilot survival (ASK FIRST), matching the dossier pattern.

## 3. Patterns to Follow

**Gate contract — `decisions:` frontmatter** (decide writes, decompose reads;
`joycraft-decide/SKILL.md:135-142`). S1/S2 extend this schema rather than invent a parallel one:
```yaml
decisions:
  - id: D1
    question: ...
    status: clarified   # open | clarified | backlogged | discarded
    choice: ...
    rationale: ...
```

**PILOT divergence marker** — every repo-local edit that diverges from `src/` gets:
```html
<!-- PILOT: diverges from src/ — see 2026-07-21-living-harness brief -->
```
(pattern at `joycraft-decompose/SKILL.md:23`, `joycraft-design/SKILL.md:136`).

**Machine gate — safeguard generator** (`src/safeguard.ts`; installed as
`.claude/hooks/joycraft/block-dangerous.sh` + `deny-patterns.txt`, exit 2 on match). The
harden pass appends patterns to these existing files; it does not add a new hook framework.

**Context-doc row + append discipline** (`joycraft-add-fact/SKILL.md:127-145`): table docs
get dated rows; frontmatter `last_updated/last_updated_by` bumped in place. The ledger
follows this shape but **prepends** (brief constraint: newest-first).

**Artifact frontmatter** — 4-field personal schema (`status/owner/created/feature`) for
feature-scoped docs; 2-field shared schema for `docs/context/*`. Ledger uses the 2-field
shared schema (it is a context doc, not feature exhaust).

**Advisory-not-applied** (`joycraft-lockdown/SKILL.md:126` "Never auto-apply", tune Tier 3
confirm-first): S6 harden and S9 promote both show exact diffs and wait for approval.

## 4. Resolved Design Decisions

> **Decision:** Line budget = **200 lines** for layer-2 docs; over-budget shards **by year**
> behind a `## Older <doc> → docs/context/archive/<doc>-<year>.md` index line at the bottom.
> **Rationale:** 200 is already the repo's enforced threshold in optimize (CLAUDE.md and
> skill files ≤200) — one number, one vocabulary. Time-ordered docs shard cleanly by time;
> the check is a MAKE_A_CHECK in optimize v2 (deterministic line count, no new hook).
> **Alternative rejected:** shard by area — creates one-home ambiguity (which area owns a
> cross-cutting decision?), violating S4. Brief's "many small files behind an index" —
> ledger rows are one-liners; per-feature files would be 47 near-empty files (RF-4 firehose).

> **Decision:** Decision-log and ledger flip to **newest-first (prepend)**; add-fact's
> "append only" rule is amended to "prepend new rows; never modify or remove existing rows."
> **Rationale:** brief constraint (b) is explicit — append-only chronological puts the
> most-relevant rows where a partial read never reaches. The 22 existing rows get reversed
> once, in this sprint.
> **Alternative rejected:** keep decision-log append-only for continuity — leaves the most
> re-read context doc (RF-4) worst-ordered for agents.

> **Decision:** S6 harden targets the **existing two enforcement surfaces only**:
> `permissions.deny` strings and `deny-patterns.txt` regexes.
> **Rationale:** both are already generated, installed, and battle-tested
> (`src/safeguard.ts`, `init.ts:411-414`); "eligible" prose = boundaries expressible as a
> command/edit pattern. Ineligible prose stays prose and is labeled so in tune.
> **Alternative rejected:** new PostToolUse/Stop hooks for semantic rules — Nate's own
> caution (don't port the 3,500-line machinery); judgment stays with the model.

> **Decision:** Boundary provenance lives **inline** as an HTML comment on the rule line in
> AGENTS.md (`<!-- origin: <failure|source> <date>, probation: <model> -->`), read by tune.
> **Rationale:** one rule, one home — a sidecar table drifts from the rules it annotates
> (Nate Rule 3); HTML comments are invisible in rendered views.
> **Alternative rejected:** `docs/context/boundary-provenance.md` table keyed by rule text —
> breaks on any rule rewording.

> **Decision:** Spec-status vocabulary unified: new-feature's spec template switches from
> `status: active` to `status: todo` (+ `mode:`), matching decompose and the queue.
> **Rationale:** two writers currently emit different initial statuses for the same
> artifact; the queue lifecycle (`todo → in-review → done`) is the settled system.
> **Alternative rejected:** leave as-is — it's exactly the "several versions of the truth"
> S4 exists to kill.

> **Decision:** Repo-local design skill re-absorbs `src/`'s "Reconcile Brief with Findings"
> step during this sprint (it's currently behind src/ while ahead on the decide checkpoint).
> **Rationale:** the reconcile step is S1-adjacent (it catches silent brief-vs-reality
> drift); carrying the divergence into another sprint compounds the merge debt.
> **Alternative rejected:** defer to pilot-graduation merge — that merge gets harder, not easier.

> **Decision:** S2 block threshold = load-bearing **and ≤50**; anchors and threshold
> defined once in `docs/context/anchors.md`.
> **Rationale:** matches CE's doc-propagation floor (≥50 doc, claude pass :125) and the
> brief's own phrasing; one definition consumed by design, decide, and S10 evals.
> **Alternative rejected:** CE's full per-artifact thresholds (≥80 code / ≥75) — code-side
> review is out of scope this sprint.

> **Decision:** S10 eval scope = the **changed skills with machine-checkable gates**
> (decompose provenance gate, session-end delete path, optimize v2 dispositions), N≥3
> fresh-subagent runs graded from the tool-call timeline; not every touched skill.
> **Rationale:** convergence's own bar ("N≥3 on anything ambiguous") applied where failure
> is destructive or gate-breaking; evaluating all ~9 touched skills triples cost for
> advisory-only surfaces.
> **Alternative rejected:** eval everything — RF-2 complacency is real but budget is finite;
> advisory steps fail soft.

**From the deposition checkpoint (2026-07-21)** — full rationale in the decision-log:

> **D1 → A:** Reaper deletes shipped folders post-merge; session-end writes the ledger row

> **D2 → hybrid:** live-head `shipped.md` newest-first under the 200-line budget; numbered

## 5. Open Questions

**All seven questions terminated clarified at the deposition checkpoint (2026-07-21)** —
outcomes in Section 4 above, the brief's `decisions:` frontmatter, and the decision-log.
D3 was punted mid-deposition and resolved the same session by the skill-taxonomy
discussion (human doors vs agent-invoked internals — see the D3 entry in Section 4 and
the decision-log row).

The original questions and option cards are kept below as the record of what was weighed
(D1–D5 mirror the brief's `decisions:` block; D6 surfaced during exploration; D7 was
asked directly from Section 4).

> **Q (D1): When does the feature folder die, and does dossier.html survive?**
> - **Option A (recommended):** Session-end writes the ledger row at `done`-graduation but
>   only **marks** the folder reap-eligible; the Reaper (optimize v2 / next session-start)
>   deletes after verifying the PR merged via `gh`. Dossier dies with the folder — the
>   ledger row carries the PR link, and the dossier's decisions are already stamped in the
>   decision-log. — Pro: deletion never outruns review; single deletion authority. Con: a
>   second touchpoint; folders linger until the next audit.
> - **Option B:** Session-end deletes immediately when it can verify the merge itself
>   (feature branch merged → delete in the same pass). — Pro: one touchpoint, no lingering.
>   Con: session-end usually runs *before* merge (it opens the PR), so this mostly no-ops
>   and the Reaper is still needed — two code paths for one behavior.
> - **Option C:** Delete at graduation, pre-merge; dossier.html moves to
>   `docs/context/dossiers/`. — Pro: fastest exhaust removal. Con: violates the brief's own
>   "only done + merged" constraint; reviewer loses spec context mid-PR.

> **Q (D2): Ledger shape?**
> - **Option A (recommended):** single `docs/context/shipped.md`, newest-first, one row per
>   feature: `| Date | Feature | What shipped | Where (paths) | PR | Owner |`, 200-line
>   budget with year-shards per the resolved budget decision. — Pro: decision-log pattern —
>   smallest + most re-read (RF-4); one grep target. Con: needs the shard check to stay honest.
> - **Option B:** `docs/ledger/<feature>.md` per-feature files behind an index. — Pro:
>   grep-addressable per feature; no shared-file contention. Con: 47 features → 47 files of
>   ~5 lines each; recreates the folder sprawl S5 is deleting.

> **Q (D3): Where does the harden pass live?**
> - **Option A (recommended):** new skill `joycraft-harden` — scan boundaries, classify
>   eligible/ineligible, propose exact `permissions.deny` + `deny-patterns.txt` diffs,
>   apply on approval, stamp provenance. — Pro: single-purpose, composable from tune and
>   session-end (S9 promote → harden); lockdown/tune stay unchanged during pilot. Con: 22nd
>   skill; +1 description against optimize's budget check.
> - **Option B:** extend lockdown — it already interviews and emits deny patterns. — Pro: no
>   new skill; natural vocabulary. Con: lockdown is greenfield-interview-shaped (asks the
>   human what to deny), harden is convert-what-exists; merging both flows muddies each.
> - **Option C:** tune Tier 3 upgrade. — Pro: harden becomes part of the assess→upgrade
>   loop. Con: tune is already the longest multi-gate skill; Tier 3 buries a destructive-ish
>   settings edit inside a broad pass.

> **Q (D4): Where does harness config (incl. model tiers) live?**
> - **Option A (recommended):** new **committed** `docs/.joycraft/config.json` beside the
>   gitignored state.json — `{ tiers: {<stage>: {intent, model}}, harness_maps: {...},
>   degradation: [...] }` with stage keys plan/orchestrate/implement/verify. — Pro: state
>   stays machine-owned+gitignored, config is human-owned+shared (they have different owners
>   and different git lifecycles); satisfies all four model-tiering requirements; JSON is
>   readable by skills and future `src/` code alike. Con: second file in `docs/.joycraft/`;
>   this repo must first migrate off legacy `.claude/.joycraft/`.
> - **Option B:** extend state.json. — Pro: one file. Con: state.json is gitignored — tier
>   config wouldn't be shared or reviewable, and upgrade rewrites the file.
> - **Option C:** markdown `docs/context/harness.md`. — Pro: human-friendly, in the context
>   layer. Con: skills and eventual `src/` code both need to parse it; prose config is what
>   S6 exists to retire.

> **Q (D5): Who scores confidence?**
> - **Option A (recommended):** authoring skills (design/new-feature) self-score against
>   anchors.md at write time; decide **audits** the scores while building the dossier and may
>   re-anchor with a note. — Pro: scores exist before decide runs (S1 provenance can cite
>   them); decide stays an auditor, not an author (RF-KILL-3: don't certify your own
>   framing). Con: two skills must learn the anchors; self-scores skew optimistic until
>   audited.
> - **Option B:** decide derives all scores when building the dossier. — Pro: one scorer,
>   consistent calibration. Con: decide scoring claims it also selected as questions is
>   self-certification; claims in docs decide never reads stay unscored.

> **Q (D6, new): What does the Reaper do with undead folders — archive or delete?**
> - **Option A (recommended):** archive-move to `docs/archive/features/<slug>/` (RF-KILL-7:
>   squash merges break git-history recovery), with a one-line reason in the disposition
>   table. Only S5's *shipped* path deletes, because extraction (ledger row) happened.
> - **Option B:** delete undead folders too, symmetrical with S5. — Pro: one behavior. Con:
>   undead folders had **no extraction** — no ledger row, no decision stamps — so deletion
>   loses the only copy; this is precisely the CE-vs-RF conflict the brief resolves in
>   favor of "delete only after extraction."
