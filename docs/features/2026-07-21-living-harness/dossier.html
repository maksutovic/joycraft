D1 · EXHAUST DELETION

When does a shipped feature folder die — and does dossier.html survive it?

Session-end runs before the merge (it is the step that opens the PR), but the brief allows deletion only for done + merged features. So the writer of the ledger row and the deleter of the folder cannot naively be the same pass. Deletion is destructive and unsupervised — this is a mandatory boundary question.

A · Mark at graduation, Reaper deletes post-merge

Recommended
  • Ledger row written at session-end while context is hot; deletion waits for verified merge (via gh)
  • Deletion never outruns PR review; reviewer keeps specs/design
  • One deletion authority (the Reaper) for both shipped and undead paths
  • Dossier dies with the folder — PR link and decision-log rows are the survivors
  • Second touchpoint: folders linger until the next optimize/session-start audit
  • Reap-eligible marker is one more state bit to keep honest
Blast radius
joycraft-session-end joycraft-optimize (Reaper) docs/features/** deleted post-merge

B · Session-end deletes when it can verify the merge

  • Single touchpoint, no lingering folders
  • Session-end precedes merge in the normal flow, so this mostly no-ops
  • The Reaper is still needed for the leftovers — two code paths for one behavior
Blast radius
joycraft-session-end delete depends on gh state at run time

C · Delete at graduation, pre-merge; dossier moves to docs/context/dossiers/

  • Fastest exhaust removal; dossier explicitly preserved
  • Violates the brief's own "only done + merged" constraint
  • Reviewer loses spec context mid-PR
  • Preserved dossiers become a new unbounded pile
Blast radius
docs/features/** deleted pre-merge docs/context/dossiers/ (new)
