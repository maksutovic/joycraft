# Testing that saves hours: the 1.9.0 testing release

Make Joycraft's tests cost the user as little time as possible in agent queues, and bring state-of-the-art testing strategy into every project, from day one or through a cleanup refactor. This ships with drift-tidy as 1.9.0.

The sources are kept outside the repository. They are a field project's test-tooling report (one machine with 14 cores, many agents, 48 hours fixing slow and flaky agent-written tests), a 10-agent SOTA research swarm, a Fable 5.2 panel ruling, and Max's direct panel Q&A. Max's goal, in his words: tests must stop feeling "like an obligation rather than a useful tool", and "getting smart about only running tests specific to that spec would save a user maybe hundreds of hours of work a month".

## Context and authorization

Max answered 8 decisions (`fault-run-location` through `worker-cap-home` above) and approved panel conclusions 2, 3 and 4 in the Q&A. The five open decisions above block only the sections that name them. Joycraft stays stack-agnostic: it names no test runner and ships no per-stack tooling. The agent knows the project's runner, and Joycraft's text says "the runner's own flag".

Rules for every goal:
- time is a fact, never a gate;
- no new file per test run;
- no machine number in a tracked file;
- every proof states its limit.

## Goals

### spec-tier

Each spec carries its own test tier.
- Setup records `focused`, `gate` and `full` commands in `joycraft.yaml`.
- Decompose and the spec template ask for the spec's own test files, never the gate.
- `queue-check.mjs` reports the gap `gate-in-spec` (exit 2) when a spec names the recorded gate or full command (Max: yes).
- `dispatch-start.mjs` prints the focused command built from the spec's check inputs.
- `checkReport` rejects a review report that ran the gate.
- Fix `joycraft-verify` line 51 against line 53.
- Drop "run the project gate one time" from the implementer agent.
- Reverse `testing-review.md`'s "do not recommend test selection".

**Done when:** a spec whose acceptance names `pnpm verify` fails queue-check with `gate-in-spec`, and a spec naming `pnpm test tests/x.test.ts` passes. The packet prints that focused command. A report that ran the gate is rejected.

### wave-gate

Decision `wave-gate-default` (open). The coordinator runs the gate alone on the integrated revision, and `delivery.mjs` refuses a push without a green gate receipt. On red:
- the spec whose inputs hold the failing file gets the fix round;
- otherwise, bisect only the failing file, newest commit first;
- a second red holds the push.

The reviewer verdict says "gate not run; due at wave end".

**Done when:** a two-wave fixture queue runs the gate twice in total, and a red gate that names a file in spec 3's inputs reopens spec 3 only.

### owner-gate-lines

`cleanup.mjs` flags a rule line outside the Commands table that names the gate ("every step must pass `pnpm verify`"). `joycraft-cleanup` offers a before-and-after rewrite as one decision. `update` shows the finding once (Max: yes).

**Done when:** an AGENTS.md line "Run `pnpm verify` after every change" gives one finding, and the Commands table row does not.

### declared-test-changes

Decompose writes a `## Test changes` section in the spec: path, class and the requiring line; the default is "none". There are three classes:
1. **Spec-mandated:** the acceptance line states the new value.
2. **Same claim, changed test:** a fault proof per file (decision `fault-run-location` = `in-place-checked`).
3. **Deleted, skipped or out of the gate:** a ledger row and an owner yes per batch.

Reviewer rules:
- Reviewer startup prints the declared and undeclared changed test files, by script.
- The reviewer blocks only an undeclared change that no line requires.
- When a brief's "no weakened tests" contradicts the feature, decompose asks once.
- A red or flaky test outside the spec's set cannot hold the spec.

**Done when:** a spec declaring class 1 for `a.test.ts` passes review with the expected value changed. An undeclared edit to `b.test.ts` with no requiring line blocks. Startup output lists both.

### fault-proof

The test-only spec, ruling rows 3 to 5:
- Faults are saved as patch files, and the old test must fail on each.
- `evidence.mjs run --patch <fault.diff>` refuses a dirty tree, applies the patch, runs, reverses it, and checks the restore by hash.
- The reviewer reruns one saved fault plus one of its own. It blocks only when the old test catches a fault that the new test misses.
- Decision `test-only-product-code` = `none`: a seam or a fix goes first, in its own spec.

**Done when:** `--patch` restores the tree byte-for-byte after a passing run and after a timeout. A test-only spec whose new test misses a saved fault fails review.

### evidence-marker

Keep `CI=1` and add `JOYCRAFT_EVIDENCE=1`. Each result carries:
- wall time;
- 1-minute load at start and end;
- the core count;
- `loaded: true` when load is above the core count;
- the failing tail of the output when the exit code is not 0.

These facts go in one receipt footer line, written before the hash.

**Done when:** a fixture command sees both variables, and the receipt footer carries the facts.

### lane-cap

Decision `worker-cap-home` = `dispatch-and-offer`. Dispatch says: when N workers share the machine, give each test run at most cores ÷ N workers, set with the runner's own flag. This replaces "rerun once, alone". Setup offers a worker cap in the project's runner config, keyed on `JOYCRAFT_EVIDENCE`, never on `CI`. Decision `test-only-lane` (open) says which specs share one lane.

### load-guidance

Decision `machine-slot` = `project-owned`, with Max's note that Joycraft *must* explain the practice. Guidance comes in this order: run less, then cap workers per run, then a slot. Joycraft explains it when it happens, with a number. At queue end it prints one line, only when runs were `loaded`. Setup explains it in an attended step. Agents get config, not prose.

### sota-page

Decision `sota-knowledge-home` (Max's note). Setup, or the test review, writes a short project-owned testing page behind a narrow map row ("a test run is slow or flaky"). The page carries about nine strong principles as the project's own decisions, in the project's stack. Joycraft-shipped playbook text is read on demand only (setup and the test review), within decision `cap-raise`.

### test-review-cleanup

The test review becomes the cleanup path for an existing suite:
1. Measure once and note the load.
2. Rank by what every run pays.
3. Find controls keyed on `CI` and nested test runners.
4. Write each approved change as a test-only spec.

A time limit or a result cache is offered only "after a measurement".

### fewer-better-tests

- `joycraft-implement` allows one test for several checks and prefers extending an existing file.
- Each user-flow check names the real boundary it crosses, or lists the mocked boundary under "Not covered".
- A new acceptance test must fail before the code exists; receipts show the order.

### session-end-pr

Session end rides the PR. It starts with a clean-tree check; on a dirty tree it reports and commits nothing of the user's. The order is: records, one tidy commit, prune, archive last, one push (decision `session-end-push-order`). After merge it does only a read-only "deployed and working" check at the next session start. No post-merge phase, no merged-PR detector, no `sessionEnd.commits` setting. This settles drift-tidy spec 12 and decision `tidy-dirty-tree`.
